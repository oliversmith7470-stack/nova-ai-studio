## 2. Adapter design — Fun-InP (`gpu-cloud/src/engines/fun-inp.js`)

The adapter is the engine interface contract: `load / generate(first_keyframe, last_keyframe, prompt, frames, steps) / unload`, with **FP16 as the required path** on T4. The live implementation is the Kaggle notebook `packages/fun-inp-proof-20261125-01/fun-inp-proof.ipynb` (9 cells, mirroring the LTX proof structure). JS-side: `buildJobSpec` (validated spec; rejects non-FP16 dtype, frame counts Wan cannot encode — `(frames-1)` must be divisible by 4 — out-of-range steps/guidance/resolution), `buildConditioning` (the exact video/mask tensor layout), `validateSpec`, plus the `FUN_INP_INTERFACE` load/generate/unload description and the `FUN_INP_PROOF` constants.

### 2.1 Verified load path (25 Nov, before the proof)

- **Pipeline:** VideoX-Fun `WanFunInpaintPipeline` (native, pinned commit `98fffa929bb373edcbfa3620e9aa05cd65a53103`, 2026-11-24). NOT the diffusers `WanImageToVideoPipeline`: the conversion's `model_index.json` declares it, but the standard pipeline builds 32 channels and cannot drive the 36-channel InP transformer (16 noise + 4 mask + 16 masked-video; native forward concatenates `[noise, mask, masked_video]` on the channel axis). Scheduler: diffusers `FlowMatchEulerDiscreteScheduler` (as the ComfyUI Fun loader constructs it).
- **Weights (scoped download, ~4.9 GB):** transformer + VAE + CLIP image encoder + tokenizer from the diffusers conversion `weizhou03/Wan2.1-Fun-1.3B-InP-Diffusers`. Verified by safetensors-header Range reads: transformer 3.13 GB / 1,013 tensors ALL BF16, `in_channels: 36`, class `WanTransformer3DModel`; VAE 0.48 GB / 194 tensors ALL F32; image_encoder 1.26 GB / 520 tensors ALL BF16. The conversion's text_encoder is 22.5 GB FP32 — too big to download; NOT used.
- **Text encoder:** umT5-XXL as transformers `UMT5EncoderModel`, weights from Kaggle Model `thiminhnht/umt5-xxl-fp16` (single file `umt5_xxl_fp16.safetensors`, 11.37 GB, 243 tensors — 242 F16 + 1 U8). Mounted read-only, zero disk. **Correction (v4, 25 Nov): the file's keys are NOT a clean transformers-format set.** Verified by the v4 load itself: the file contains `shared.weight` (the T5 embedding, as in the canonical conversion) but NOT the tied duplicate `encoder.embed_tokens.weight`, and it carries one non-weight tensor, `spiece_model` (U8 — the SentencePiece model bytes packed into the file). The earlier "keys in transformers format" claim was based on tensor counts/dtypes only, not the key names — see §3 v4.
- **Disclosed substitution:** the native pipeline expects its custom `WanT5EncoderModel` class; the proof loads the SAME umT5-XXL weights into transformers' `UMT5EncoderModel` instead, because the native class's parameter names differ from the checkpoint's transformers-format keys and a remap could not be verified without the weights in hand. Same weights, same architecture, same FP16 arithmetic; the native pipeline only calls `text_encoder(input_ids, attention_mask)[0]` and reads `.dtype`, both of which `UMT5EncoderModel` satisfies. The native class's `fp16_clamp` safety net is absent in the transformers class — the notebook finite-checks the embeddings and records inf/NaN as a finding.
- **Precomputed prompt_embeds are NOT passed:** the native `__call__` does `in_prompt_embeds = negative_prompt_embeds + prompt_embeds`, which is list concatenation for internally-encoded embeds but ELEMENT-WISE ADDITION for directly-passed tensors — the precomputed-embeds path is broken in this native pipeline. The proof calls the pipeline with `prompt=` (string) + `negative_prompt=""`, so encode_prompt runs the text encoder internally. Consequence: diffusers **model CPU offload** is enabled — all four modules resident would be 16.24 GB > the 15.36 GB T4 (encoder 11.37 + transformer 3.13 + VAE 0.48 + CLIP 1.26).
- **Conditioning:** video tensor `[1,3,17,576,1024]` float in [0,1] — frame 0 = first keyframe, frame 16 = last keyframe, middle frames zero; mask_video `[1,1,17,576,1024]` — 0 at frames 0/16 (keep), 255 at frames 1–15 (generate). `clip_image=None` (native pipeline runs CLIP on a black image and zeroes the result). Mask semantics verified from the native source (`masked_video = init_video * (mask_condition < 0.5)`; `mask_video == 255` everywhere = T2V mode).
- **Comparability:** same dragon keyframes as LTX run 6 (sha256 asserted in-notebook: first `b746e5fa…`, last `c8218a25…` — the dataset now serves the run-6 keyframes; the v1 script asserted the run-4/5 hashes), same run-6 prompt, 17 frames, 1024×576, seed 42. 50 steps, guidance 6.0 (native defaults).
- **FP16 proof:** dtype audits before AND after sampling assert zero BF16 parameters across transformer + VAE + CLIP + text encoder; per-step callback records latent dtypes; keyset checks assert the remapped/surgered weight keys match the native classes exactly. **Correction (v7, 25 Nov): the conversion's weight keys do NOT map 1:1 onto the native classes.** The transformer needs a verified remap (1,013 → 983, 30 dropped) and CLIP needs verified surgery (520 → 392); both are proven.
